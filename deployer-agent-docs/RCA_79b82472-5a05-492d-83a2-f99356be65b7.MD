# RCA — stationexus.store intermittent "aucune création" / backend stops responding

## Problem statement
Live site https://stationexus.store intermittently shows no creations ("aucune création") and nothing loads, as if the backend stops responding. Reported as intermittent.

## Verdict
The backend pod is being **OOMKilled** at the tier_0 memory limit (512Mi), restarting, and during the ~40–60s restart window every `/api/*` call fails with nginx "Connection refused" to the uvicorn upstream. That is the window where the home page renders "aucune création". Between restarts the app serves normally (hence intermittent). Two compounding causes: (1) code loads large base64 images into memory, (2) the tier ceiling is too low for that footprint.

## Evidence
### Pod OOMKilled at the tier memory limit
- `get_pod_events` (active run 79b82472…):
  - `last terminated: OOMKilled (exit 137) at 2026-11-06T00:17:48Z, restarts=1` on pod `…-qf4tv`.
  - `Liveness probe failed: HTTP probe failed with statuscode: 503`, `Startup probe failed: …503`, and `Readiness probe failed: Get http://10.74.36.20:8080/health: context deadline exceeded` — the backend became unresponsive before/around the kill.
- `get_tier`: tier_0 "Starter" → memory request 200Mi, **memory_limit 512Mi**, cpu_limit 250m, replicas 2. OOMKilled (not bare exit 137) at this ceiling = genuine memory-limit hit.

### The symptom window maps exactly to the restart
- `fetch_app_logs` around 00:17:48–00:18:01 shows nginx returning, repeatedly:
  - `connect() failed (111: Connection refused) while connecting to upstream … "GET /api/creations"`
  - same for `/api/categories`, `/api/settings`, `/api/journal`, `/api/membership/plan`, `/api/atelier/bootstrap`, `/health` — upstream `http://127.0.0.1:8001` (uvicorn) is down during the restart.
- At 00:15:32: `upstream timed out (110) while reading response header from upstream … "GET /health"` — backend unresponsive (memory pressure) → liveness 503 → container killed → restart loop.
- Outside those windows the same endpoints return `200 OK` in bulk — confirming intermittent, not a hard outage.

### Memory drivers in source (run source, inspected in sandbox — OOM itself NOT reproduced because the sandbox is given more memory than tier_0)
- `backend/server.py:580` `list_creations`: `docs = await db.creations.find(q, {"_id": 0}).sort("order",1).to_list(1000)` — loads up to **1000 full creation documents including the heavy base64 `poster` / `bg_image` / `gallery` / `chapters` fields into RAM**, then strips them in Python via `_lighten()`. The projection does not exclude the heavy fields at the DB layer, so the full payload is materialized in memory on every `/api/creations` call.
- Posters/backgrounds are stored as base64 **data URIs inside Mongo docs** (`_serve_image`, `poster`/`bg_image` fields).
- `backend/server.py:637` `/creations/{cid}/poster` + `_thumb()`: decodes base64 posters with PIL (`Image.open`) per request and keeps an in-process cache `_THUMBS` of up to 300 JPEG blobs (`server.py:617`). Concurrent poster/thumbnail requests (the home page fires many `…/poster?w=360|900`) decode large images in memory simultaneously.
These together push the 2 small replicas over 512Mi under load.

## Recommended fixes
1. **Code (E1)** — cut the backend memory footprint:
   - In `list_creations` (and any list endpoint), exclude heavy base64 fields in the Mongo **projection** itself, e.g. `find(q, {"_id":0, "poster":0, "bg_image":0, "gallery":0, "chapters":0, "episodes":0, "intention_images":0})` instead of `to_list(1000)` of full docs + `_lighten()`. Also consider paginating instead of `to_list(1000)`.
   - Avoid storing/serving posters as in-DB base64; move images to object storage and serve by URL. At minimum, bound/evict `_THUMBS` more aggressively and cap concurrent PIL decodes.
2. **User → Deployment Panel → Resources** — raise the tier above tier_0 (512Mi limit is the confirmed OOM ceiling). tier_1/"Launch" or higher gives headroom and stops the restart loop while the code fix lands.
3. **Minor (Code)** — the backend has no `/health` route (`GET /health` → 404 from uvicorn); liveness/readiness currently pass only because nginx fronts it. Adding a lightweight `/health` endpoint makes probes more reliable.

## Not the cause
MongoDB connectivity is fine — queries return 200 in bulk outside the restart windows; no Mongo timeout/auth errors in logs. No code exception/traceback; failures are purely "upstream down" during OOM restarts.
